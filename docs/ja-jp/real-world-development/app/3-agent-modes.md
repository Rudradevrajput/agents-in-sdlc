プロジェクトに小さな機能を追加しました。しかし、より大規模な変更には、さらに堅牢なプロセスが必要です。GitHub Copilot app は組織の既存のフローに沿って作業できるように設計されており、適切なものを適切な方法で構築できます。このレッスンから数回にわたり、一般的なエージェント主導の開発プロセスを実践します。issue から新機能を作成し、コードが有効で機能が期待どおりに動作することを確認し、最終的にプロジェクトへマージします。

> [!NOTE]
> 機能のワークフローでは、同じセッションを使います。通常は作業するファイルの種類ごとに異なるセッションや PR を使用しますが、ここでは中心的な概念に集中できるように手順を簡略化します。

このレッスンでは、次の操作を行います。

- GitHub issue から新しいエージェント セッションを開始します。
- **Plan** モードで要件を定義します。
- **Autopilot** モードで新機能を実装します。
- コードをレビューします。
- ブラウザー キャンバスで機能を手動で検証します。

この機能の作業を続けながら、リポジトリの命令を更新し、既存の `quality-checks` スキルをカスタマイズし、MCP による検証を追加して QA エージェントを作成し、機能 PR を作成します。

## シナリオ

Tailspin Toys のカタログが増え、訪問者がゲームをカテゴリと発行元で絞り込めるようにする必要があります。バックログの issue には機能が記載されていますが、カテゴリを組み合わせる方法などはコーディング前に合意が必要です。Plan モードで決定し、範囲を定めた実装を Autopilot に任せます。

## 背景

AI コーディング エージェントを開発フローに導入しても、基本は変わりません。むしろ、基本はさらに重要になります。多くの開発者は、次のようなフローで作業します。

1. 必要な作業の詳細を記載した issue から始めます。
2. 実装計画を作成します。
3. コードを作成してレビューします。
4. テストを実行して検証します。
5. 新機能を手動で検証します。
6. プル リクエスト (PR) を作成します。
7. コードレビューと継続的インテグレーションが成功したら、コードをマージします。

> [!NOTE]
> 正確な手順はチームや組織によって異なりますが、ほとんどの場合は上記の流れを基にしています。

標準的な方法を守ることで、AI が生成したコードが要件を満たし、人が作成したコードと同じレビュー プロセスを通るようにします。

## セッション モード

**セッション モード**は、エージェントの自律性を制御します。プロンプト フィールド下のドロップダウンから設定し、いつでも変更できます。

- **Interactive**: ユーザーとエージェントが共同で作業します。エージェントは変更を提案し、続行前に入力を待ちます。
- **Plan**: エージェントが最初に計画を作成します。実行前に計画をレビューして承認します。
- **Autopilot**: エージェントが入力を待たずに、コードの作成、テストの実行、反復を自律的に行います。

まず Plan モードで開始して計画をレビューし、その後 Autopilot で実装します。

## issue からセッションを開始する

開始前に、星評価の PR がマージされ、ローカルの `main` が最新であることを確認します。

1. サイドバーの **Sessions** で Tailspin Toys リポジトリのフォルダーを選択し、リポジトリ上部のナビゲーションで **Issues** を選択します。**Allow users to filter games by category and publisher** を開きます。これはテンプレートに含まれる issue です。新たに作成する必要はありません。
2. **New session** を選択し、更新済みの `main` に基づく **new working tree** を選択します。

    ![GitHub Copilot app の issue ビューで New session ボタンを矢印で示した画面](../../../_images/app-new-session-from-issue.png)

3. issue がセッションに添付されていることを確認し、モード セレクターで **Plan** を選択します。

> [!NOTE]
> Node.js または npm が見つからない場合は、エージェントに `node --version` と `npm --version` を実行させます。ターミナルでは動作するのにセッションで動作しない場合は、アプリの PATH またはバージョン マネージャーの設定を確認し、アプリを完全に終了して再起動します。失敗した操作とチェックを再試行してください。エージェントが npm を見つけられないという理由だけで npm を再インストールしないでください。

## 絞り込み機能を計画する

計画を立てることで、Copilot がコードを書く前にアプローチを確認できます。issue から開始したため、Copilot は機能リクエストをすでにコンテキストとして把握しています。次の内容を送信します。

```plaintext
Build this feature.
```

Copilot の質問に回答し、issue の受け入れ条件に照らして計画を確認します。カテゴリと発行元による絞り込み、アクセシブルなコントロール、データ アクセスの変更、テストが含まれていることを確認してください。複数カテゴリの組み合わせ方や、一致するゲームがない場合の動作など、不明確な点を話し合います。

計画には、プロジェクトの既存ツールを使った lint、ユニット テスト、E2E テスト、型チェックを含めます。絞り込み機能の実装とテストに範囲を絞り、品質確認ワークフローを終えてから PR を作成します。計画の修正は承認前に依頼し、後で検証できるよう issue の URL と合意した補足事項を控えておきます。

## Autopilot を明示的に承認する

計画に納得したら、**Approve and implement this plan** を選択するか、使用中のバージョンで同様の項目を選択します。承認によってモードも切り替わると思い込まず、モード表示が **Autopilot** になっていることを確認します。

Copilot は計画に沿って反復し、コードを生成してテストを実行します。

> [!NOTE]
> 承認するとすぐに実装が始まる場合があります。先に計画を確認してください。依存関係が不足している、またはポートが競合していると報告された場合は、チェック完了と判断する前にセットアップの問題を解決します。自分が起動したサーバーだけを停止してください。

## 実装をレビューして検証する

生成されたコードは、他のコードと同様にマージ前にレビューします。

1. **Changes** を開き、絞り込み機能の実装とテストを確認します。
2. 複数カテゴリと発行元の組み合わせも含め、結果を issue と承認済みの補足事項に照らし合わせます。既存のリポジトリ命令に従っていることも確認します。
3. lint、ユニット テスト、E2E テスト、型チェックの結果を確認します。スキップされたチェックは成功ではありません。
4. 実装を承認する前に失敗を解消し、影響するチェックを再実行します。Playwright の E2E 設定はビルドしてプレビューを配信し、ローカル サーバーを再利用する場合があります。テスト対象が前のレッスンではなく、この worktree のサーバーであることを確認します。

## 新機能を確認する

コードに問題がないように見えても、実際に動くでしょうか。前と同じようにアプリを起動し、ブラウザー キャンバスでサイトを開きます。

1. 次のプロンプトを使い、アプリを起動してブラウザー キャンバスでページを開くよう Copilot に依頼します。

    ```plaintext
    Start the app and open it in the browser canvas.
    ```

2. しばらくするとアプリが起動し、Copilot app 内にブラウザー ウィンドウが開きます。
3. カテゴリを選択し、結果がそのカテゴリに合うことを確認します。フィルターを解除してから発行元を選び、結果がその発行元に合うことを確認します。
4. カテゴリと発行元のフィルターを組み合わせ、issue と承認済みの計画に合う結果になることを確認します。複数カテゴリに対応する場合は、合意した組み合わせ動作を確認します。
5. ゲームが一致しない組み合わせを試し、空の状態を確認します。フィルターを解除またはリセットして、全件が再表示されることも確認します。
6. 確認が終わったら、次のプロンプトを使い、このセッションで起動した開発サーバーを停止するよう Copilot に依頼します。

    ```plaintext
    Stop the dev server and close the browser canvas.
    ```

## 次のレッスンでも同じセッションを使う

絞り込み PR はまだ作成またはマージしないでください。レッスン 4 から 8 まで、このセッション、worktree、ブランチを使います。次はカスタム命令を絞り込みコードに適用し、スキルと QA の改善を追加してから、レッスン 8 で変更をまとめた PR を作成、マージします。開発サーバーを停止した後、セッションをアイドル状態にしてかまいません。次のレッスンで同じセッションに戻ります。

## まとめと次のステップ

異なるエージェント モードを使って機能を作成、レビューしました。GitHub issue からエージェント セッションを開始し、**Plan** モードで要件を定義し、**Autopilot** モードで実装し、コードをレビューして、ブラウザー キャンバスで手動検証しました。
